# Phase 17 Plan 03 — Gap closure: a duplicate key inside a merge source is rejected (PIPE-04, PIPE-05)

<objective>
Close the single blocking gap from `17-VERIFICATION.md` (`status: gaps_found`, 13/14 must-haves): the strict validator silently ACCEPTS a document whose duplicate key lives inside a mapping used only as a merge source, so the phase's headline promise — "without weakening duplicate-key rejection" (ROADMAP goal, PIPE-05, plan 17-01's `must_haves` truth 8 and its standing prohibition) — does not hold for a reachable input.

Reproduced against the real validator: `<<: &b {language: ru, language: en}` and `<<: [&b {language: ru, language: en}]` both return `None` from `validate()` and load with last-wins (`language: 'en'`), while the identical duplicate written anywhere else is rejected. Root cause: `_StrictSafeLoader.flatten_mapping` snapshots and projects only the node that CARRIES the merge, and `construct_mapping` scans only `self._own_keys.get(id(node), node.value)` for that same node; a `MappingNode` used purely as a merge source is never passed to `construct_mapping`, because PyYAML splices its raw pairs into the parent with `merge.extend(value_node.value)`. The phase introduced the weakening — before the merge fix every `<<` document was rejected outright.

Purpose: restore the invariant "an explicitly duplicated key written ANYWHERE in the document, including inside a mapping that is only ever used as a merge source, yields exactly one structured reject row" — with the SAME row contract (`PipelineConfigError(path="", message=f"found duplicate key ({key!r})", line=<1-based duplicate key node>)`), the same zero-write 400 envelope, and no regression to the merge bound, the oracle corpus or the override/first-source-wins semantics (D-03).

Output: the pristine merge-source snapshot + duplicate scan inside the existing pre-mutation window in `flatten_mapping` (via a factored-out `_check_own_keys` helper), the unit RED corpus additions in `tests/unit/test_pipeline_config_merge.py`, the end-to-end proof in `tests/unit/test_http_pipeline_config.py`, and — in a third, separately scoped task — the WR-01 nested-merge teaching message (a graded behaviour change carrying its own RED test) together with the advisory IN-01 / IN-02 / IN-03 items.

**Scope note (unchanged from 17-01/17-02):** one production file only. `PipelineConfigModel` and its locked four-key `extra="forbid"` schema (D-01), `MAX_PIPELINE_CONFIG_CHARS = 20000`, the `Loader=_StrictSafeLoader` argument, the `yaml.SafeLoader` subclass hierarchy (research Pitfall 9), the HTTP route and `composition/` are all untouched. No `web/` change (D-08). No PR constraint is added or removed.
</objective>
