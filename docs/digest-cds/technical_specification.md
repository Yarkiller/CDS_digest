# Техническая спецификация — Digest CDS

Функциональные и нефункциональные требования для реализации Digest CDS (Concept 3 — Editorial UI), извлечённые из 31 user story и 68 критериев приёмки (Given/When/Then). Каждое функциональное требование описывает одну проверяемую функцию и имеет однозначный pass/fail тест. Нефункциональные требования (раздел 2) покрывают производительность, SLO, безопасность, аудит и надёжность; технологический стек — в разделе 3.

## 0. Процесс разработки и тестирования

Разработка Digest CDS ведётся по обязательному циклу **Red–Green–Refactor**.

Для новых функций, исправлений, рефакторинга и изменений поведения необходимо:

1. Сначала написать минимальный автоматизированный тест.
2. Запустить его и убедиться, что он падает по ожидаемой причине.
3. Реализовать минимальный production-код для прохождения теста.
4. Запустить новый тест и весь существующий набор тестов.
5. Выполнить рефакторинг только при полностью успешных тестах.
6. Повторить цикл для следующего поведения.

Действует правило:

> NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST

Тесты должны проверять поведение системы, а не наличие mock-объектов. Моки применяются только при необходимости и после понимания реальных зависимостей. Исключения допускаются для конфигурационных, сгенерированных и одноразовых прототипных файлов либо с явным согласованием.

### Сквозной контентный контракт

1. Материалом считается только самостоятельная статья, подготовленная агентом. Она создаётся из исходного текста, полученного транскрибацией внешнего видео или импортом текста, и дополняется результатами уточняющего поиска, проверки и анализа.
2. Статья может быть практическим гайдом по установке и использованию технологии или описанием нового подхода. Необработанный транскрипт, ссылка на видео, видеофайл и аудиофайл не являются материалом и не отображаются в качестве его содержимого.
3. Видео/аудио допускаются только как внешняя входная сторона pipeline. Система может кратковременно обработать источник для получения текста, но не сохраняет видео или аудио как материал и не встраивает видеоплеер на странице статьи.
4. Карточка знаний и дайджест формируются из опубликованной статьи, а не напрямую из транскрипта.
5. При первом уместном упоминании сложного термина, подхода или технологии, по которым уже есть отдельная статья, UI и текст должны давать внутреннюю ссылку на эту статью. Связь должна быть взаимной либо дополнена блоком связанных материалов. Для provenance допускается отдельная ссылка на внешний первоисточник.

### Оптимизация

**Предложение:** объединить дублирующиеся сценарии redirect через `returnUrl` (US-02 AC2 — deep-link после login; US-06 AC2 — ссылка из письма после login) в одно требование FR-6.

**Проверка:** зависимости US-01 → US-02 → US-06 сохранены; FR-5 (редирект на текущий выпуск без `returnUrl`) и FR-13 (ссылка в письме) остаются отдельными. Логика исходных историй не нарушена — **оптимизация принята**.

## 1. Функциональные требования

### 1.1 Вход (US-01, US-02)

1. Система должна создавать сессию и предоставлять доступ к защищённым страницам Digest CDS при вводе на `login.html` валидного email с доменом `@sberbank.ru` или `@omega.sbrf.ru` и верных учётных данных с последующей отправкой формы, чтобы авторизованный сотрудник СВА получил доступ к сервису.
2. Система должна отклонять вход и отображать под полем email сообщение о корпоративном домене СВА при попытке входа с email вне разрешённых доменов (например `@gmail.com`), чтобы сессия не создавалась для неавторизованных доменов.
3. Система должна отображать inline-ошибку валидации у поля email и не отправлять запрос к auth API при отправке формы входа с пустым полем email, чтобы пользователь исправил ввод до обращения к серверу.
4. Система должна отображать inline-ошибку валидации у поля пароля и не отправлять запрос к auth API при отправке формы входа с пустым полем пароля, чтобы пользователь исправил ввод до обращения к серверу.
5. Система должна перенаправлять пользователя на страницу текущего выпуска (`issue`) после успешной аутентификации без параметра `returnUrl`, чтобы пользователь сразу начал чтение без лишней навигации.
6. Система должна перенаправлять пользователя на URL из параметра `returnUrl` после успешного входа при переходе по deep-link или ссылке из письма без активной сессии (предварительный redirect на login с `returnUrl`), чтобы пользователь попал на целевой выпуск, материал или другой исходный экран, а не только на текущий выпуск по умолчанию.

### 1.2 Выпуск (US-03, US-04, US-05, US-06)

7. Система должна отображать номер/период выпуска, заголовок издания и оглавление (IssueTOC) со списком материалов при открытии `issue` авторизованным сотрудником СВА при наличии опубликованного текущего выпуска с хотя бы одним материалом, чтобы пользователь за минуту понял состав дайджеста.
8. Система должна отображать empty state «выпуск готовится» (или эквивалент) с CTA в архив или базу знаний при открытии `issue` при отсутствии опубликованных материалов в выпуске, чтобы пользователь не видел «битую» пустую страницу без пояснения.
9. Система должна отображать EditorialCallout с датой окончания цикла голосования и CTA перехода на `voting` (например «Выбрать тему») на странице `issue` при открытом цикле голосования, чтобы сотрудник знал срок и перешёл к выбору темы.
10. Система должна отображать в callout на `issue` информацию о закрытом голосовании и не показывать доступный CTA выбора темы при закрытом цикле голосования, чтобы сотрудник не переходил к недоступному голосованию.
11. Система должна отображать под заголовком материала в оглавлении выпуска 1–2 предложения поля audit-dek на языке аудита без обязательного знания ML-терминов при просмотре карточки/строки материала на `issue` с заполненным полем audit-dek, чтобы сотрудник оценил пользу до чтения статьи.
12. Система должна скрывать блок audit-dek или показывать согласованный с редакцией нейтральный fallback при просмотре материала без audit-dek на `issue`, чтобы UI не отображал пустую строку-заглушку.
13. Система должна включать в доставленное письмо еженедельного дайджеста ссылку на соответствующий выпуск (`issue` / archive item) на сайте после успешной отправки дайджеста админом при наличии подписки/учётки у сотрудника, чтобы сотрудник читал выпуск в привычном канале и переходил в издание на сайте.

### 1.3 Материал (US-07, US-08, US-09)

14. Система должна отображать подготовленную статью в prose-колонке, оглавление секций (TOC), заголовок материала и при наличии блок provenance/ссылку на внешний источник при открытии `material` авторизованным пользователем, чтобы пользователь спокойно усвоил обработанный текст и мог отличить статью от первоисточника.
15. Система должна прокручивать страницу или переходить к соответствующей секции при клике по пункту TOC на странице материала с несколькими секциями, чтобы пользователь навигировал по содержанию статьи.
16. Система должна открывать `material` с содержимым подготовленной статьи при выборе материала авторизованным Data Analyst на `issue` или `knowledge`, чтобы аналитик изучил детали метода или приёма.
17. Система должна отображать подготовленную статью с различимым типом формата «статья» при открытии материала авторизованным Data Scientist, чтобы пользователь видел обработанный и проанализированный текст, а не видеоплеер или необработанный транскрипт.
18. Система должна отображать состояние «материал не найден» с навигацией назад (выпуск / база) при открытии URL с несуществующим id материала, чтобы пользователь вернулся к доступному контенту.
19. Система должна явно отображать badge формата материала и список тегов при просмотре материала с форматом и хотя бы одним тегом на `issue` или `material`, чтобы читатель сразу понял тип контента.
20. Система должна отображать badge формата материала при открытии карточки материала без тегов так, чтобы отсутствие тегов не нарушало вёрстку, чтобы читатель видел тип контента без ошибок отображения.

### 1.4 Голосование (US-10, US-11, US-12, US-13)

21. Система должна сохранять ровно один голос пользователя за выбранную тему и отображать статус «Ваш голос:» с названием выбранной темы при подтверждении голоса авторизованным сотрудником в открытом цикле при наличии хотя бы одной темы на ballot и отсутствии ранее отданного голоса, чтобы пользователь влиял на тему ближайшего разбора и видел зафиксированный выбор.
22. Система должна хранить не более одного одновременного голоса пользователя в открытом цикле при попытке отдать второй независимый голос за другую тему без смены текущего выбора, чтобы действовало правило «один голос на цикл».
23. Система должна не отправлять голос и отображать ошибку «Выберите тему» при нажатии подтверждения на открытом ballot без выбранной темы, чтобы пользователь явно выбрал тему перед голосованием.
24. Система должна отображать статус о том, что голос не отдан, и не устанавливать ни один radio/option темы в состояние selected по умолчанию при открытии `voting` пользователем в открытом цикле, который ещё не голосовал, чтобы пользователь не подтвердил чужой выбор по ошибке.
25. Система должна отображать лидирующую тему по числу голосов отдельно от блока «ваш выбор» при показе лидера пользователю, который ещё не голосовал, чтобы лидер не выглядел как уже сделанный выбор пользователя.
26. Система должна сохранять голос за тему B, обновлять счётчики и отображать «Ваш голос: B» при выборе темы B и подтверждении смены пользователем, уже проголосовавшим за тему A в открытом цикле, чтобы пользователь исправил выбор при новой информации.
27. Система должна отклонять изменение голоса и отображать сообщение о закрытом цикле при попытке смены голоса пользователем после закрытия окна цикла голосования, чтобы голос оставался неизменным после дедлайна.
28. Система должна отображать у каждой темы на ballot краткое описание на языке аудита и число материалов (включая явное «0 материалов» при отсутствии привязок) при открытии ballot сотрудником СВА для тем с описанием и привязанными материалами, чтобы сотрудник голосовал осознанно.
29. Система должна отображать число материалов у темы без описания на ballot и не показывать вводящий в заблуждение пустой блок описания, чтобы сотрудник видел количество материалов без ложного контекста.

### 1.5 База знаний (US-14, US-15, US-16, US-17)

30. Система должна отображать список результатов с ненулевой релевантностью к запросу или честный empty state при вводе смыслового поискового запроса на `knowledge` авторизованным пользователем при наличии релевантных карточек в индексе, чтобы пользователь нашёл карточку знаний по смыслу, а не только по точному названию.
31. Система должна не выполнять поиск и отображать inline-валидацию «Введите запрос» при отправке поискового запроса, состоящего только из пробелов, на `knowledge`, чтобы пустой запрос не обрабатывался как валидный.
32. Система должна оставлять в выдаче только материалы, помеченные для аналитика, при включении фильтра роли «Data Analyst» (или эквивалентных тегов SQL/BI/DQ) и выполнении поиска/просмотра на `knowledge` авторизованным Data Analyst, чтобы аналитик не получал в качестве единственного результата фильтра только материалы `#RAG`/`#LLM` без analyst-меток.
33. Система должна возвращать выдачу к состоянию без ролевого ограничения с сохранением текста запроса при сбросе активного фильтра Data Analyst на `knowledge`, чтобы пользователь расширил поиск без потери введённого запроса.
34. Система должна включать в выдачу релевантные ML/experiment материалы, доступные к открытию, при поиске по методу/теме ML или включении фильтра роли Data Scientist на `knowledge` авторизованным Data Scientist при наличии ML-материалов в индексе, чтобы Data Scientist готовил разбор и углублял практику.
35. Система должна открывать страницу материала с ожидаемым заголовком при переходе Data Scientist из результата поиска в материал, чтобы связь search → detail была однозначной.
36. Система должна отображать empty state «ничего не нашли» (или аналог) без подмены выдачи нерелевантным ML-топом при завершении поиска с запросом и фильтром/интентом аналитика при отсутствии подходящих карточек в индексе, чтобы Data Analyst не принял ML-выдачу за релевантный ответ.
37. Система должна сбрасывать фильтры или возвращать фокус в поле поиска для нового ввода при нажатии «Сбросить фильтры» / «уточнить запрос» в empty state после поиска Analyst, чтобы пользователь начал новый поиск.

### 1.6 Разборы (US-18, US-19, US-20, US-21)

38. Система должна отображать список разборов с названием, датой и статусом (например опубликован / анонс) при открытии `razbory` авторизованным пользователем при наличии хотя бы одного опубликованного или анонсированного разбора, чтобы пользователь нашёл нужную встречу или публикацию.
39. Система должна отображать empty state с пояснением и CTA (например к голосованию) при открытии `razbory` при отсутствии разборов, чтобы пользователь понял причину пустого списка и перешёл к следующему действию.
40. Система должна отображать longread и TOC с переходом к секции по клику на пункт TOC при открытии `razbor` опубликованного разбора с несколькими секциями, чтобы читатель навигировал по секциям метода и применения в аудите.
41. Система должна сохранять оглавление разбора доступным для навигации в пределах viewport при прокрутке страницы разбора на поддерживаемых ширинах экрана при sticky TOC, чтобы читатель навигировал по longread без возврата к началу страницы.
42. Система должна начинать скачивание или открытие файла `.ipynb`, соответствующего разбору на экране, при нажатии «Скачать .ipynb» / «Открыть» Data Scientist на разборе с прикреплённым notebook, чтобы Data Scientist воспроизвёл демонстрацию.
43. Система должна отображать CTA скачивания notebook как недоступный (disabled) или отсутствующий с понятной подписью на странице разбора без прикреплённого файла `.ipynb`, чтобы пользователь не получал обещание nbconvert без файла.
44. Система должна отображать видимый блок «Оценка качества» (или эквивалент) с числовыми/табличными метриками при открытии `razbor` Data Scientist для разбора с заполненным блоком метрик (precision/recall или согласованный набор), чтобы Data Scientist оценил пригодность метода для аудита.
45. Система должна явно указывать тип «обзор» на странице разбора без метрик, помеченного как intro/обзор, при открытии Data Scientist, чтобы отсутствие метрик не маскировалось под полный экспериментальный разбор.

### 1.7 Админ — shortlist и рассылка (US-22, US-23, US-24, US-25, US-26, US-27, US-31)

46. Система должна отображать список кандидатов shortlist (до 5) с идентификаторами/названиями и порядком ранжирования при открытии `admin-digest` пользователем с ролью админ при сформированном shortlist недели, чтобы админ утвердил состав недели.
47. Система должна возвращать HTTP 403 (недостаточно прав) при открытии URL админки пользователем без роли админ, чтобы неавторизованный пользователь не видел рабочий shortlist.
48. Система должна отображать empty state «кандидатов нет» с возможностью обновить при открытии `admin-digest` админом при пустом shortlist, чтобы админ понял отсутствие кандидатов и инициировал обновление.
49. Система должна отображать кандидата как включённого и сохранять это состояние на сервере при выполнении Approve / «Включить в дайджест» админом для кандидата shortlist в состоянии «не включён», чтобы админ явно включил материал в рассылку.
50. Система должна исключать кандидата из состава рассылки и явно отражать исключение в UI при выполнении Reject / «Исключить» админом для включённого кандидата, чтобы админ контролировал состав дайджеста без «молчаливого» checkbox без семантики.
51. Система должна отображать различимый статус draft или ready у каждой строки shortlist при просмотре списка админом при наличии кандидатов с обоими статусами, чтобы админ не отправил незавершённый материал.
52. Система должна блокировать отправку дайджеста с сообщением убрать/дождаться ready при попытке отправки админом при наличии хотя бы одного включённого в selection кандидата со статусом draft, чтобы незавершённый материал не ушёл в рассылку.
53. Система должна отображать превью (modal/страница) с составом, соответствующим текущему selection, при открытии «Предпросмотр письма» админом при выборе хотя бы одного ready-материала, чтобы админ проверил финальный вид дайджеста перед отправкой.
54. Система должна отображать ошибку превью и не считать отправку «проверенной» при нажатии «Предпросмотр письма» админом при недоступности сервиса превью из-за ошибки сервиса, чтобы админ не отправил дайджест без проверки.
55. Система должна отображать score и не менее 2 читаемых факторов при раскрытии «Почему в топе» / tooltip у score админом для кандидата shortlist с score и набором факторов, чтобы админ принял editorial-решение на основе обоснования.
56. Система должна отображать «обоснование недоступно» при просмотре строки shortlist админом при недоступности факторов скоринга, чтобы UI не показывал выдуманные проценты.
57. Система должна обновлять selection согласно действию за одну операцию при нажатии «Выбрать все» или «Оставить топ-3» админом на shortlist из нескольких кандидатов, чтобы админ ускорил triage под дедлайн.
58. Система должна изменять состояние только снятого вручную item при снятии одного item после batch select, сохраняя выбор остальных отмеченных кандидатов, чтобы частичная коррекция selection не сбрасывала весь выбор.
59. Система должна инициировать рассылку, отображать успех в UI и добавлять/обновлять выпуск в архиве при подтверждении «Отправить дайджест» админом при selection из хотя бы одного ready-материала, успешно просмотренном превью (если политика требует) и не выполненном цикле отправки недели, чтобы дайджест был доставлен сотрудникам СВА и зафиксирован в архиве.
60. Система должна не создавать некontролируемый дубликат рассылки и отображать сообщение о том, что дайджест уже отправлен, или требовать явный re-send по политике при повторном нажатии отправки админом после отправки дайджеста этой недели, чтобы исключить двойную рассылку.
61. Система должна отображать ошибку сети, не помечать рассылку успешной и сохранять selection для повторной попытки при подтверждении отправки дайджеста админом при недоступности сети, чтобы админ повторил отправку без потери выбора.

### 1.8 Архив (US-28)

62. Система должна открывать содержимое выбранного прошлого выпуска (материалы периода) при выборе выпуска на `archive` авторизованным сотрудником при наличии хотя бы одного прошлого выпуска в архиве, чтобы сотрудник вернулся к материалам предыдущих недель.
63. Система должна отображать empty state с CTA на текущий выпуск при открытии `archive` при пустом архиве, чтобы пользователь перешёл к доступному контенту.

### 1.9 Post-v1 (US-29, US-30)

64. Система должна отображать результат прохождения (число верных / %) и фиксировать прохождение как событие активности (если сбор активности включён) при запуске и ответе на все вопросы карточки с 5–10 вопросами у опубликованного материала или разбора, чтобы читатель проверил понимание.
65. Система должна не отображать CTA квиза или отображать его как disabled без битой ссылки при открытии материала читателем при неопубликованной карточке с вопросами, чтобы пользователь не переходил к несуществующему квизу.
66. Система должна принимать конфиг и отображать его как активный при загрузке валидного YAML и сохранении на экране конфигурации админом, чтобы админ менял источники и правила пайплайна без деплоя.
67. Система должна отклонять сохранение с конкретной ошибкой валидации (строка/поле) и оставлять прежний валидный конфиг активным при сохранении невалидного YAML админом, чтобы некорректный конфиг не заменил рабочий.
68. Система должна возвращать HTTP 403 при открытии URL конфигурации пользователем без роли админ, чтобы управление YAML-конфигами было доступно только админу.

## 2. Нефункциональные требования

Классические NFR ниже описывают качество сервиса (производительность, доступность, безопасность, наблюдаемость). Ограничения предметной области («не более 1 голоса», «shortlist ≤ 5», «HTTP 403 для не-админа» и т.п.) являются **функциональными / бизнес-правилами** и уже зафиксированы в разделе 1; их трассировка — в §2.7.

Целевые численные пороги v1 — ориентиры для корпоративного сервиса во внутреннем контуре; при согласовании с инфраструктурой СВА/Cloud.ru допускается уточнение без изменения FR.

### 2.1 Производительность

| ID | Требование | Целевой порог (v1) |
|----|------------|-------------------|
| NFR-P1 | Открытие страницы текущего выпуска (`issue`) для авторизованного пользователя при наличии опубликованных материалов | p95 времени ответа API/SSR ≤ **1,5 с**; интерактивный UI без блокировки > 2 с |
| NFR-P2 | Открытие страницы материала (`material`) с подготовленной статьёй и TOC | p95 ≤ **2 с** |
| NFR-P3 | Семантический поиск в базе знаний (`knowledge`) по осмысленному запросу при тёплом индексе | p95 ответа поиска ≤ **2 с**; при деградации — явный статус «поиск временно недоступен», без подмены выдачи |
| NFR-P4 | Загрузка shortlist на `admin-digest` (до 5 кандидатов со score) | p95 ≤ **2 с** |
| NFR-P5 | Асинхронный контентный pipeline (FoundryModels: транскрибация/импорт → статья) | не блокирует чтение уже опубликованного контента; прогресс/ошибка задачи видны админу или в операционном логе |

Измерение: серверные метрики latency (p50/p95) по ключевым эндпоинтам + выборочные synthetic checks в рабочее время.

### 2.2 Доступность (SLO)

| ID | Требование | Целевой порог (v1) |
|----|------------|-------------------|
| NFR-A1 | Доступность веб-сервиса чтения (login, issue, material, knowledge, voting, archive, razbory) в рабочие часы СВА (пн–пт 09:00–19:00 MSK) | **≥ 99,5 %** календарного месяца (исключая согласованные окна обслуживания) |
| NFR-A2 | Плановое обслуживание | не чаще 1 раза в неделю; анонс ≥ 24 ч; предпочтительно вне рабочих часов |
| NFR-A3 | Деградация при недоступности FoundryModels | опубликованный контент и голосование остаются доступны; новые задачи pipeline переходят в failed/retry с понятной ошибкой, без потери уже сохранённых статей |
| NFR-A4 | Деградация при недоступности почтового канала | UI админа показывает ошибку отправки; selection shortlist сохраняется (см. FR-61); повторная попытка без потери triage |

### 2.3 Безопасность и изоляция контура

| ID | Требование |
|----|------------|
| NFR-S1 | Вход и регистрация допускаются только с email-доменов `@sberbank.ru` и `@omega.sbrf.ru` (см. ADR-0003, FR-1–FR-2) |
| NFR-S2 | Эндпоинты и страницы админки (`admin-digest`, конфигурация пайплайна) недоступны пользователям без роли админ (HTTP 403; FR-47, FR-68) |
| NFR-S3 | Секреты (ключи FoundryModels, БД, почта) хранятся только в контуре Cloud.ru / секретах окружения VM; не коммитятся в репозиторий |
| NFR-S4 | Внешние публичные зарубежные LLM/Whisper API не используются для обработки контента (ADR-0002) |
| NFR-S5 | Видео- и аудиофайлы внешнего источника не сохраняются и не публикуются как материал; в системе — только подготовленная статья, provenance и внутренние связи (NFR-CONTENT / сквозной контракт) |

### 2.4 Логирование и аудит действий админа

| ID | Требование |
|----|------------|
| NFR-L1 | Система пишет структурированный audit-лог по действиям админа: Approve/Reject кандидата, batch-selection, предпросмотр письма, отправка дайджеста, сохранение YAML-конфига (post-v1). Запись: кто (user id / email), когда (UTC), что (action + entity id), исход (success/fail + код ошибки) |
| NFR-L2 | Audit-лог неизменяем для роли админ через UI (append-only); доступ на чтение — админ и/или операционная роль по политике контура |
| NFR-L3 | Логируются события безопасности: успешный/неуспешный login, отказ по домену, HTTP 403 на админ-URL |
| NFR-L4 | Операционные логи приложения (ошибки API, сбои FoundryModels, сбои рассылки) коррелируются request-id; персональные данные в логах минимизируются (email — по необходимости для аудита, без паролей и токенов) |
| NFR-L5 | Срок хранения audit-лога админ-действий — не менее **90 дней** (или дольше по политике СВА); бэкапы PostgreSQL включают данные, необходимые для расследования инцидентов рассылки |

### 2.5 Надёжность данных и UX-качество

| ID | Требование |
|----|------------|
| NFR-R1 | Резервное копирование Supabase/PostgreSQL выполняется по расписанию команды (ответственность за бэкапы на self-hosted VM — следствие ADR-0004); восстановление проверяется не реже 1 раза в квартал |
| NFR-R2 | Sticky TOC страницы разбора остаётся в пределах viewport на поддерживаемых ширинах при прокрутке longread (US-19 / FR-41) — usability-ограничение layout |
| NFR-R3 | Клиентская валидация не заменяет серверные проверки доменных ограничений, прав админа и идемпотентности рассылки |

### 2.6 Контентная политика (качество / compliance)

| ID | Требование |
|----|------------|
| NFR-CONTENT | Видео- и аудиофайлы внешнего источника не должны сохраняться или публиковаться как материал; материалом может быть только подготовленная статья с provenance и внутренними ссылками на связанные статьи |

## 3. Технологический стек и окружение

Сводные технологические решения v1. Обоснования и альтернативы — в ADR; при расхождении приоритет у принятого ADR.

| Область | Решение | Источник |
|---------|---------|----------|
| Хостинг приложения | Виртуальная машина **Cloud.ru** | [ADR-0002](../adr/0002-cloud-ru-foundrymodels-deployment.md) |
| ML / обработка контента | API **FoundryModels** Cloud.ru (транскрибация/импорт текста, суммаризация, анализ, теги, эмбеддинги); без публичных зарубежных API и без локального Whisper на VM | ADR-0002 |
| СУБД | **Self-hosted Supabase** (PostgreSQL + **pgvector**) на отдельной VM через **Docker Compose**; базовый URL/ключи конфигурируемы; managed Supabase Cloud и managed PostgreSQL Cloud.ru не используются | [ADR-0004](../adr/0004-self-hosted-supabase-on-vm.md) |
| Деплой БД и сервисов | Self-hosted Supabase (Docker Compose) на отдельной VM; доступ через адаптер `supabase-integration` | ADR-0004 |
| Доступ пользователей | Только email-домены `@sberbank.ru`, `@omega.sbrf.ru` (фиксированный список в конфиге) | [ADR-0003](../adr/0003-email-domain-restriction.md) |
| Frontend — канон дизайна | Статический Editorial UI (`design-frontend/`) — источник экранов, токенов и UX Concept 3 | `design-frontend/`, UI-SPEC |
| Frontend — приложение ДЗ | **Vite + React + React Router + Tailwind CSS** в каталоге `web/`; визуальные токены переносятся из `design-frontend/styles/tokens.css` | `web/`, раздел 3.3 |
| Тесты UI | **Playwright** (`tests/`, `playwright.config.js`) | TDD / acceptance |
| Post-v1 (вне ядра) | Публичный лидерборд активности — после v1 | [ADR-0001](../adr/0001-public-leaderboard-gamification.md) |

### 3.3 Frontend-приложение (минимум для сдачи ДЗ)

Стек сдаваемого UI-приложения:

| Слой | Выбор |
|------|-------|
| Сборка / dev-сервер | Vite |
| UI-фреймворк | React |
| Роутинг | React Router |
| Стилизация | Tailwind CSS (theme на базе design tokens Concept 3) |
| Автотесты | Playwright |

Минимум **три** основные функции, которые должны работать в React-приложении (mock-данные допустимы):

1. **Выпуск и материал** — просмотр текущего выпуска (`issue`) и открытие подготовленной статьи (`material`).
2. **Голосование** — выбор темы цикла и подтверждение голоса (`voting`).
3. **База знаний** — поиск/фильтры и список материалов (`knowledge`).

`design-frontend/` остаётся эталоном макетов; production backend (auth, SMTP, FoundryModels) в объём ДЗ не входит.

### 3.4 Границы контура

1. Весь runtime-стек и секреты живут в контуре Cloud.ru (приложение + PostgreSQL + вызовы FoundryModels).
2. Исходное видео/аудио — внешний вход pipeline; в БД и UI попадает статья и provenance, не медиафайл как материал.
3. Ответственность за бэкапы, обновления и отказоустойчивость self-hosted Supabase (PostgreSQL) на VM лежит на команде продукта (следствие ADR-0004).
4. Зависимость от доступности FoundryModels учитывается в NFR-A3 и NFR-P5; при смене провайдера потребуется адаптер ML-pipeline (ADR-0002).

### 3.5 Окружения (минимальный набор)

| Окружение | Назначение |
|-----------|------------|
| local | Разработка и TDD; Compose с PostgreSQL/pgvector по возможности близко к prod |
| staging (рекомендуется) | Проверка рассылки, прав админа, интеграции FoundryModels на непродуктивных данных |
| production | VM Cloud.ru, рабочий контур СВА |

Точные версии ОС образа VM, теги образов Compose и параметры sizing VM фиксируются в runbook/деплой-документации при выводе в prod и не дублируются здесь.
