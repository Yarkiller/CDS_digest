# AI-промпты для анализа логов (Шаг 7)

Практические промпты для разбора структурированных JSON-логов backend (`structlog`)
и логов фронтенда (Vercel) с помощью AI-агента.

## Формат логов

Backend пишет по одной JSON-строке на событие в `stdout`:

```json
{"event": "request_finished", "level": "info", "timestamp": "2026-10-05T11:20:31.004Z", "request_id": "b1f2...", "method": "GET", "path": "/health", "status": 200}
{"event": "request_client_error", "level": "warning", "timestamp": "...", "request_id": "...", "method": "POST", "path": "/voting/votes", "status": 403}
{"event": "request_server_error", "level": "error", "timestamp": "...", "request_id": "...", "method": "GET", "path": "/knowledge", "status": 503}
```

Уровень задаётся переменной `LOG_LEVEL` (`debug | info | warning | error`); по умолчанию `info`.

## Промпт 1. Найти инциденты за период

```text
Ты — SRE. Ниже JSON-логи backend за последний час.
1. Сгруппируй события по request_id.
2. Найди запросы, завершившиеся статусом 5xx, и восстанови цепочку по request_id.
3. Для каждого инцидента укажи: путь, метод, статус, время, вероятную первопричину.
4. Отдельно перечисли 4xx-всплески (предполагаемый источник: фронтенд или клиент).
Верни таблицу и список рекомендаций. Не выдумывай поля, которых нет.

<логи>
...
</логи>
```

## Промпт 2. Классифицировать типовые ошибки

```text
Ниже JSON-логи. Классифицируй каждое событие уровня warning/error по категориям:
auth (401/403), not_found (404), rate_limit (429), upstream (5xx),
validation (400/422), прочее.
Для каждой категории: количество, пример request_id, первый и последний таймстемп.
Отметь категории, которые выросли относительно предыдущего окна.
```

## Промпт 3. Проверка гипотезы

```text
Гипотеза: рост 503 на /knowledge вызван недоступностью Supabase,
а не ошибками приложения.
По логам подтверди или опровергни: есть ли 5xx только на маршрутах,
ходящих в БД; совпадают ли таймстемпы с ошибками readiness-пробы
(/health/ready); нет ли 4xx на тех же маршрутах.
Приведи конкретные строки логов как доказательства.
```

## Промпт 4. Пост-деплойный чек

```text
Сравни логи до и после деплоя (метка времени деплоя: <ISO>).
Назови: новые типы событий, исчезнувшие события, изменение доли 5xx,
самый частый медленный/падающий маршрут. Заверши вердиктом:
rollback / keep с наблюдением / стабильно.
```

## Как подавать логи агенту

- Backend (Railway): скачать логи сервиса и передать как JSONL.
- Frontend (Vercel): экспорт Runtime Logs; для клиентской диагностики
  использовать события Яндекс.Метрики (см. `integration_documentation.md`).
- Перед передачей в AI удаляйте `Authorization`/токены и персональные данные:
  backend намеренно не логирует их (`T-01-03`), но проверяйте входные дампы.
